# ADR 0012：业务作答幂等与只读对账（Issue 7 第三阶段）

- 状态：Implemented，待独立 PR 合并与测试环境验收
- 基线：已合并的 PR #12、#13；沿用事务、dataEpoch、deleteId、服务端序号和持久 outbox
- 范围：新作答的业务身份、确认映射、题目/每日计数与离线只读对账

## 根因与约束

旧协议以 attempt.id 判断重放。两台设备可以从同一练习快照提交相同 clientOpId，却生成不同本地 ID；两条事实都会被接受，按设备分区合并的统计也会累计两次。只增加服务端唯一键不能收敛客户端计数、会话提交标记和已捕获的上传快照。

本阶段将新作答计数按事实归属，服务端确定业务事实 ID；确认时同时收敛本地事实、统计和会话引用。旧聚合无法反推实际答案或原始日期，保留其基线，只读报告未知项，不执行修复或补造历史。

## 业务身份和首次事实

业务键为 `(openid, dataEpoch, sessionId, questionId, clientOpId)`。完整非空练习会话身份才参与业务去重；缺少身份的旧流水按已有事实 ID 处理，不推断两条旧记录属于同一次操作。

服务端将业务键规范编码后生成 `op_<SHA-256>` 作为文档和公开事实 ID。同业务并发写入必定访问同一事务文档；客户端本地 ID 仅标识待确认提交。不同操作、账号或清空代次使用不同地址。

同业务、同题目版本、同 selected/answer/score 的重试返回首次事实，包括首次 createdAt、costMs 和学习日。时间或用时变化不会产生新事件；答案、题目版本或得分变化返回 OPERATION_CONFLICT，不覆盖已接受事实。此约束不代替服务端验分，题目可信版本与内容校验仍依赖 #5。

有业务身份的旧事实先通过只读查询查找，并在事务内重读。查询前的档案修订与事务内不一致时最多重新预检三次，不能将读失败当成不存在。多条旧业务事实或不能归属的旧别名返回 LEGACY_OPERATION_CONFLICT，保留原事实及聚合。新业务 ID 还检查历史 ID 命名空间冲突，冲突时失败，不覆盖历史文档。

## 新提交接口与原子确认

新增 `studySync action=commitAttempts`，必须带 attemptProtocol=2。旧服务端不认识 action，会明确拒绝而不执行旧 update 写入。不得为兼容而静默退回旧写接口。get 的增量协议继续为 syncProtocol=2。

```json
{"action":"commitAttempts","attemptProtocol":2,"token":"<session>","dataEpoch":0,"attempts":[{"id":"at_<local>","sessionId":"ps_1","questionId":"q1","clientOpId":"ps_1:q1","questionVersionId":"v1","selected":["A"],"answer":["A"],"score":1,"costMs":100,"createdAt":1793491200000,"projection":{"version":1,"date":"2026-11-01","subject":"公基","chapter":"测试"}}],"stats":{}}
```

```json
{"ok":true,"attemptProtocol":2,"dataEpoch":0,"acceptedAttemptIds":["at_<local>"],"attemptReceipts":[{"submittedId":"at_<local>","attempt":{"id":"op_<hash>","sessionId":"ps_1","questionId":"q1","clientOpId":"ps_1:q1"}}],"stats":{"records":{},"daily":{}},"aiEpoch":0,"aiStale":false}
```

响应示例省略完整事实字段和聚合内容。acceptedAttemptIds 确认的是本批本地提交 ID；attemptReceipts 为每个确认提供完整首次事实。二者必须一一对应并完整覆盖本批事务，缺少任何一项就保留整批；不能只凭任意 ok:true 或一个陌生 ID 删除 outbox。

客户端验证确认身份、内容、代次、唯一性及已有 ID 的内容冲突后，在草稿上替换本地未确认 ID、移动对应事实计数、更新 submitted.attemptId，合并云端题目/每日计数，移除明确确认的队列项，并一起同步落盘。写盘失败保留原事实 ID、原内存、原磁盘和队列。事实首次确认后内容不再改变。

恢复读到规范事实时可以先归一化本地临时事实和计数，但不据此移除 outbox，仍需原提交获得明确确认。已排队的旧快照在发送前归一化其中的旧引用；只替换该快照中已有的事实，不加入捕获之后的答案。别名缓存仅留在进程内，队列排空即释放；跨重启依赖持久规范事实与原待传项重放。

新协议最多 32 条：每条最坏为业务地址读、历史 ID 冲突读、首次写，连同档案读写共 98 次事务操作。历史业务查询在事务外，通过修订校验衔接；事务内不使用 where。旧 update 的 48 条上限保持不变，但账号启用新协议后，旧 update 返回 ATTEMPT_PROTOCOL_REQUIRED。整体清空保留该协议要求。

## 计数来源与兼容

新事实保存 projection.version=1、date、subject、chapter；服务端接受后标记 confirmed=true。采用客户端首次学习日，不由重试设备重新决定日期。计分、用时、时间、日期及字段结构必须有效；客户端将负作答用时规范为 0。

客户端待确认作答使用临时 `__fact__<localId>` 分区，确认或从恢复结果取得事实证据后移除；云端题目 answerBy 和每日/科目/章节 by 只保留一个 `__server_facts_v1__` 计数分区。服务端仅在同事务首次创建业务事实时递增该分区，重试不递增；客户端快照中的临时分区和服务端分区全部剥离，不能作为云端计数写入依据。

只有服务端写入该分区，因此既有按分区取 max 的合并规则在这里是同一写入者的单调序列，不会重复叠加不同设备的同一业务提交。计数分区数量不随已确认流水逐条增长，避免把完整事件历史再次复制进单个聚合文档。客户端确认要求服务端返回的计数覆盖本批事实，移除临时贡献后合并该权威计数；不同日期/用时的重试采用首次事实。新协议只接受整批确认，部分事务回包保留全部待传项后幂等重试。

部分批次成功时，新事实对应的计数已经可恢复，完整会话/设置快照仍在最后一批发布。

已有设备/legacy 分区继续作为历史基线按原规则合并，不全量重算，不扣减猜测值。历史事实不回填日期、科目或答案；历史基线导入仍依赖客户端提供的数据，不能将其视为防作弊或已通过事实证明的统计。掌握度、连续答对、复习计划和收藏/设置仍沿用字段版本规则，本阶段只对作答次数、正确/错误数、每日数量及用时建立事实计数保证。

## 错误与恢复

| 错误 | 行为 |
| --- | --- |
| OPERATION_CONFLICT | 同业务内容不同，整批失败；保留队列，停止无效重试 |
| LEGACY_OPERATION_CONFLICT / ATTEMPT_ID_CONFLICT | 历史身份歧义或地址冲突，保留数据并只读对账 |
| BAD_FACT_METADATA / ATTEMPT_PROTOCOL_REQUIRED / BAD_ACTION | 结构或版本不支持，不写入；需要修复数据或协调版本 |
| READ_STATS_FAILED / READ_ATTEMPTS_FAILED | 访问失败，不能作为不存在继续写 |
| TX_FAILED / SYNC_RETRY_REQUIRED | 无确认，保留同一提交有界重试 |
| INVALID_ATTEMPT_ACK / PERSIST_ACK_FAILED | 客户端不能持久确认，保留原 ID 与待传项 |

syncNow 对不可重试的业务/版本错误返回具体错误码；传输、事务和检查点故障继续沿用三次上限。没有自动选择冲突答案或删除冲突队列的操作。

## 只读对账

```sh
npm run audit:learning -- --input /path/to/offline-snapshot.json
```

只读取指定的单账号离线快照，输出 JSON，不连接云、不写回文件；测试仅使用合成数据。报告 scope=answer_counters_v1，区分：

- consistent：本快照范围内的新事实贡献、计数缓存及会话引用一致，不代表已同步或掌握度等所有派生字段已验证。
- issues：已证明的重复业务/事实冲突、孤立贡献、缺口、计数缓存不符、非法数值或提交标记缺少实际事实。
- incomplete：未发现上述已证明差异，但存在旧账本缺失、旧事实未归属或旧聚合未知来源；不能宣称完整对账通过。

退出码分别为 0、2、3；无法读取/解析输入或用法错误为 1。报告不输出答案、令牌、个人资料。旧聚合大于现存明细不直接判为重复；明细所证明的计数下界大于缓存，则能明确报告缺口。工具不补答案、不生成日期、不删除事实、不自动修复。

## 验证、发布与剩余风险

双设备同一会话、同一业务操作生成不同本地 ID 的用例在 PR #13 基线复现两条事实和重复统计，修复版收敛为一条；覆盖不同日期/用时、并发、改答案、不同真实操作、丢 ACK/重启、确认落盘失败、非法确认映射、多批次/排队旧引用、账号/清空隔离及自动下一题上下文。事务替身记录最坏批次 98 次操作；64 条事实仍只产生一个服务端计数分区。累计计数/用时超出安全整数范围时事务回滚，不确认或丢弃事实。只读对账使用冻结输入和 CLI 文件前后比较，验证不修改数据及历史未知分类。

发布前在独立环境验证业务查询的 `(openid, sessionId, questionId, clientOpId)` 和带 dataEpoch 的等值索引、增量索引、事务冲突重试和微信存储限制；旧写入器必须先停止/排空。先具备新后端，再通过现有版本机制升级客户端。旧客户端在已启用账号上的写入会拒绝，待升级后才能补传；本次未执行部署、真实数据库读写或付费模型调用。

回滚不得取消账号的新协议要求、唯一业务地址或恢复旧快照写接口，否则可能重复计数。保留规范事实及持久 outbox，优先向前修复；不把删除数据作为回滚策略。仍需真实环境验收、历史差异人工处理、冲突操作处理流程、掌握度等后续事实派生及 #11 的仓储/写盘优化；#7 保持 Open。
