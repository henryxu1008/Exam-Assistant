# ADR 0010：持久作答队列与按 ID 确认（Issue 7 第一阶段）

- 状态：PR #12 已合并；后续业务确认映射升级见 ADR 0012，真实环境验收仍待完成
- 范围：现有客户端 store、practice 页和 studySync；沿用 ADR 0009 的事务、身份与清空代次
- 关联：#7、#3、#11；不依赖 Go 后端迁移

## 问题与边界

数组下标不代表哪些不可变事实已被云端确认。历史数组经过恢复、迁移或重排后，保存的下标不能证明其前面的每条作答都已提交；整批成功才推进下标也无法保存前面批次的进度。此外，页面不能在本地保存失败时锁题并显示提交成功。

本阶段只解决作答的持久提交、重试与确认。启动全量恢复、快照合并、收藏/设置字段版本冲突规则均沿用现有实现；聚合仍是设备分区计数器合并，不宣称服务端已按全部事实重建聚合。

## 本地提交契约

按账号存储的同一份档案新增本地元数据：

```json
{"attemptOutbox":{"version":1,"pending":[{"id":"at_<stable-id>","questionId":"q1"}]}}
```

`pending` 保存未确认事实的副本，`attempt.id` 同时是稳定同步操作 ID。它与练习提交的 `clientOpId` 不同：后者仍用于本地会话幂等；服务端当前以 `(openid, attempt.id)` 检查不可变事实。不同 fact ID 即使携带相同 clientOpId，也不属于本阶段的服务端业务去重保证。

`submitAttempt()` 在草稿上同时计算事实、派生统计和会话标记，加入 outbox，成功同步写入账号档案后才返回 `ok:true`。写盘失败返回 `PERSIST_ATTEMPT_FAILED`，原内存档案、计数和提交标记保持原状，页面保留选择并提示重试。

所有档案写盘改用同步检查点，防止较早的异步全量写覆盖已提交的作答或确认。其他修改仍通过 persist 节流。这会增加答题/确认时主线程的全量序列化成本；尚未减少历史写放大，测量和分仓留给 #11。队列异常不会被重建为空，也不会清除真实流水。

## 发送与确认契约

只从已落盘的档案提取待传事实和快照。作答事实仍以顶层 attempts 发送，每批最多 48 条，最后一批才附完整档案，维持提交标记与实际答案的可恢复性。

studySync 在事务内检查账号、dataEpoch 和不可变内容，成功提交后返回：

```json
{"ok":true,"dataEpoch":0,"acceptedAttemptIds":["at_<stable-id>"],"aiEpoch":0,"aiStale":false}
```

客户端要求确认列表存在、ID 唯一且全部属于本批次、dataEpoch 与发起时一致。只移除被明确确认的 ID，并把出队结果同步写入同一账号档案后再更新内存。缺失/非法确认、传输失败、事务失败、检查点写盘失败都保留可重试状态。若仅确认合法子集，只持久移除该子集并停止本轮，下一轮发送剩余项；当前服务端事务仍是整批成功或回滚。

已确认批次的进度立即落盘，后续批次失败只重发剩余 ID。云端成功但 ACK 丢失时重发相同事实，已有不可变文档构成幂等回执，不新增集合。相同 ID、相同内容重复确认；相同 ID、不同内容返回 ATTEMPT_CONFLICT，不确认任何 ID。

## 恢复、升级与清空

- 首次读到没有 attemptOutbox 的旧档案时，将已有真实流水按 ID 去重入队并落盘；忽略旧数组游标。已上传事实会安全重放一次。仅有聚合、没有原始答案的旧档案不伪造流水。
- 恢复得到的远端事实不进入本地待传队列，原本的未确认本地事实和进度保留。
- 账号切换、令牌变化、清空代次仍使用现有上下文失效保护。迟到确认不得影响另一个账号或新一轮登录；原账号待传项留存，重登后可幂等重放。
- 整体清空或恢复更高 dataEpoch 时，旧队列随旧档案作废；持久 deleteId 优先于上传。AI 清空也继续优先确认，旧 AI 代次不阻断合法学习事实。各代次不相互重放。
- 未改变原始流水保留政策，不新增后台自动清理。不得单独删除未确认 outbox；显式账号清空按现有流程删除。

## 验证与发布约束

故障替身运行真实 store 和 studySync，覆盖本地保存失败、历史重排/时钟回拨、升级重放、48 条后的批次失败、重启、丢失 ACK、非法/部分确认、确认写盘失败、在途追加、队列损坏、切账号迟到确认；沿用双设备清空/AI 清空及管理员权限回归。历史重排用例在基线 store 上复现漏传，修复后通过。没有连接真实学习数据库。

先在独立测试环境验证 SDK 事务和存储配额/耗时，再协调发布：旧客户端可忽略新增确认字段，新客户端遇到旧服务端缺少 acceptedAttemptIds 时会保留队列并重试。因此应先具备新服务端确认协议，再发布客户端；不可将缺少确认视为成功兼容。此变更不执行云函数部署或数据库写入。

回滚客户端到旧版会重新启用不可靠的数组进度；优先向前修复。任何服务端回滚仍须保留正向确认、不可变事实、事务及代次保护。同步失败时本地持久队列可供后续重放，不应为了消除重试标记而清空它。

第三阶段将新提交升级为业务 ID 映射与每批 32 条，见 [ADR 0012](0012-business-idempotency-and-readonly-reconciliation.md)；本文保留第一阶段契约背景。

第二阶段的稳定服务端增量游标、前台/网络恢复拉取与有界重试见 [ADR 0011](0011-incremental-recovery-and-lifecycle-sync.md)。#7 仍需服务端事实/聚合对账及业务幂等约束；不能关闭整个 Issue。
