# 学习存储基线（Issue #11，2026-11-02）

当前单次作答经过真实 store.submitAttempt，保留既有全部合成历史，测量 JSON 序列化及一次持久提交。
存储替身只在进程内保存 JSON 字符串，不读写用户数据、不调用云或 AI。每个样本使用独立 Node 进程，
每场景 5 次；Node v24.22.1 / Linux x64。原始样本和运行信息见同目录 JSON。

```bash
npm run bench:learning -- --sizes 1000,10000 --runs 5
```

| 既有作答 | 既有 AI 消息 | 新作答后整档大小（MB，十进制） | 提交中位耗时（ms） | JSON 序列化中位耗时（ms） | 提交后观测 heap 最大值（MiB） |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 0 | 1.29 | 26.55 | 8.21 | 22.51 |
| 1,000 | 1,000 | 1.79 | 27.40 | 8.14 | 25.94 |
| 10,000 | 0 | 12.87 | 212.25 | 72.76 | 110.16 |
| 10,000 | 10,000 | 17.86 | 263.39 | 73.75 | 138.31 |

各场景每次作答均写学习文档 1 次，写入字节数等于整档大小。次数已固定，但字节成本仍随全部历史增长。
样本包含已确认事实及其原题快照；AI 场景额外包含相同数量的固定长度合成消息，没有调用模型。

这些是 Node 的 CPU/序列化基线，不包含微信原生存储桥、磁盘、实际设备、配额或真实云同步成本。
heap 仅在提交前后采样，受 GC 影响，不是整个提交的内存峰值，不能直接推断微信设备内存。
五次样本不是统计性能保证；不把本机数值作为 CI 时间阈值。

## 对 #11 的实施建议

现有快照和 outbox 保障优先保留。下一步先提取用户隔离的本地 repository，再把已确认不可变历史与
活动状态/outbox 分开保存，减少新作答反复序列化历史。原题版本可探索去重存储，但必须保持离线追溯。
格式迁移须有备份、幂等、写盘中断恢复及账号/清空代次回归，不能直接凭本基线修改真实档案。

本轮只提供可重复基线，没有实现分段存储、迁移或真实微信性能验收，#11 保持 Open。
